--------------------------------------------------------------------------------
ROADMAP MAINTENANCE POLICY: N-1 SLIDING-WINDOW & STATUS TRACKING
--------------------------------------------------------------------------------
- The roadmap maintains a rolling window: it displays the current/immediate past
  release ($N-1$) for baseline context, followed by active upcoming development
  milestones ($N$, $N+1$).
- Status Notation Policy (Modeled after Social Digest):
  * All milestones and feature items are annotated with explicit progress indicators:
    - [x] Completed item / feature
    - [-] In-progress item / active development
    - [ ] Planned / not started item
  * When work commences on an item, mark it immediately as [-] [IN-PROGRESS].
  * Mark an item as [x] [COMPLETED] when implementation is finalized, upon user
    confirmation, or inferred when development transitions to another part of the roadmap.
- When a new version is built, its completed specifications are recorded, and any
  versions older than $N-1$ are pruned to keep the document focused and actionable.
- Whenever any code change, bug fix, packaging adjustment, or feature refinement is
  made during a release cycle, it MUST be recorded immediately in the current release
  section of roadmap.txt and CHANGELOG.md (even if it occurs after the initial version
  number bump).

CORE ARCHITECTURAL INVARIANTS
================================================================================
- Core modules must NEVER import from plugins/.
- Heavy translation runtimes must remain isolated inside plugins/translation/.
- Speaker diarization uses wespeakerruntime as the primary ONNX embedding engine.
- Real-time progress updates with percentage, status messages, and estimated time.
- Diagnostic logs written to OS standard logging locations.
- Offline-first architecture: core processing functions locally without internet.
- 0 MB Default GPU Footprint: Base installer contains 0 MB of CUDA bloat; GPU features are purely optional and provisioned on demand.

================================================================================
1. PREVIOUS RELEASE: TRANSLATION DEPENDENCIES & DIARIZATION UI RESPONSIVENESS (Completed in v3.3.23)
================================================================================

[x] 1.1 ADDED PYTORCH TO TRANSLATION PLUGIN RUNTIME
---------------------------------------------------
- Discovered that the translation plugin setup reads directly from `plugins/translation/requirements-runtime.txt` instead of falling back to core `ENV_CONFIGS`, which omitted PyTorch completely from pip installs.
- Added `torch>=2.4.1` to `plugins/translation/requirements-runtime.txt` to resolve `name 'torch' is not defined` errors.

[x] 1.2 TRIGGERED TRANSLATION SPEC REBUILD
------------------------------------------
- Bumped `translate` feature version to `2.14` in `runtime_manager.py` to trigger a clean, automated self-healing build for all users.

[x] 1.3 RATE-LIMITED DIARIZATION LOGGING IN UI
----------------------------------------------
- Implemented rate-limiting for speaker detection status updates logged to `self.log_activity` in `processing.py`.
- Prevents deep-cloning all story objects and history snapshots on every tqdm tick, eliminating application freezes on long audio files.

================================================================================
2. CURRENT RELEASE: QPROCESS BUFFER DRAINING & SPEAKER DETECT PROGRESS DETAIL (Completed in v3.3.24)
================================================================================

[x] 2.1 RESOLVED QPROCESS STDOUT RACE CONDITION ON EXIT
-------------------------------------------------------
- Discovered that when the translation subprocess finishes and exits, the final `"finished"` JSON message is sometimes left unread in the QProcess stdout buffer because the `finished` slot did not read standard output before unregistering.
- Explicitly called `read_output()` inside the `finished` slot in `translation.py` to safely drain and parse any remaining payload data, enabling instant, reliable completion.

[x] 2.2 IMPLEMENTED DYNAMIC SPEAKER DETECT PROGRESS DETAIL
----------------------------------------------------------
- Replaced the generic hardcoded progress message placeholder with the actual, dynamic subprocess status message in `processing.py`.
- Keeps the user informed of active background steps (such as VAD, signature extraction, and AHC clustering) in real-time, eliminating the perception of being stuck.
