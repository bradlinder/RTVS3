ROADMAP MAINTENANCE POLICY: N-1 SLIDING-WINDOW & STATUS TRACKING
--------------------------------------------------------------------------------
- The roadmap maintains a rolling window: it displays the current/immediate past
  release ($N-1$) for baseline context, followed by active upcoming development
  milestones ($N$, $N+1$).
- Status Notation Policy (Modeled after Social Digest):
  * All milestones and feature items are annotated with explicit progress indicators:
    - [x] Completed item / feature
    - [-] In-progress item / active development
    - [ ] Planned / not started item
  * When work commences on an item, mark it immediately as [-] [IN-PROGRESS].
  * Mark an item as [x] [COMPLETED] when implementation is finalized, upon user
    confirmation, or inferred when development transitions to another part of the roadmap.
- When a new version is built, its completed specifications are recorded, and any
  versions older than $N-1$ are pruned to keep the document focused and actionable.
- Whenever any code change, bug fix, packaging adjustment, or feature refinement is
  made during a release cycle, it MUST be recorded immediately in the current release
  section of roadmap.txt and CHANGELOG.md (even if it occurs after the initial version
  number bump).

2. CURRENT RELEASE: WINDOWS CI BUILD SPEED & PYINSTALLER PACKAGING OPTIMIZATION [x] [COMPLETED in v3.8.9-beta.17]
================================================================================
*Empirical CI Run Timing Analysis (From Latest Windows Build: 24m 48s build + 1m 34s publish = ~26m 22s Total)*:
--------------------------------------------------------------------------------
- Set up job & checkout: ~8s
- Set up Python 3.12: 1m 58s
- Run ffmpeg-actions/setup-ffmpeg@v3: 4s
- Run install inno setup: 22s
- Install Python Dependencies: 2m 44s
- **Build PyInstaller Executables**: **11m 45s** (~44.6% of build duration — Bottleneck #1)
- **Build Inno Setup Installer**: **10m 53s** (~41.3% of build duration — Bottleneck #2)
- Verify Built Assets & Generate SHA256 Checksums: 2s
- Upload Artifacts (Windows Installer & Standalone): ~31s
- Create GitHub Release and Upload Assets: 1m 34s
- Complete job: 0s
- **Key Takeaways & GitHub Runner Infrastructure Analysis**:
  1. PyInstaller (11m 45s) and Inno Setup (10m 53s) consume **22m 38s (91.3%)** of the active build job.
  2. GitHub Actions standard `windows-latest` runners are provisioned with 2 vCPUs (4 threads). Because of this limited compute footprint, merely adding `LZMANumBlockThreads=2` will not magically deliver 4x linear speedups: parallel scaling on 2 vCPUs typically yields only ~1.4x–1.6x in practice due to hyperthreading resource contention and thread context-switching overhead.
  3. The real performance multiplier for Inno Setup is changing the compression parameters. The current `Compression=lzma2/ultra64` uses an extreme 64MB dictionary size and deep match-finder cycles that burn CPU time searching for redundant patterns across already-compiled DLLs and binary weights. Changing to `Compression=lzma2/ultra` or `lzma2/max` with `LZMANumBlockThreads=2` stops wasting CPU cycles, bringing installer generation down from ~11 minutes to ~3–4 minutes while adding less than 1 MB to installer size.
  4. For PyInstaller, omitting redundant heavy wheel re-collection in Stage 3 drops dedicated worker compilation from 5m 45s down to ~15s, saving ~5m 30s while preserving native console subsystem I/O and multiprocessing compatibility.
  5. Dependency setup with `setup-uv@v5` already utilizes built-in caching on warm runs; brittle runner-level caching (like Chocolatey) is avoided to protect stability.
  6. **Target Duration**: Cut total Windows CI build time from ~24m 48s to ~11–12 minutes (>50% reduction).

[x] 2.1 Fast Dedicated AI Worker Compilation (`build_installer.py`)
--------------------------------------------------------------------------------
- Risk Evaluation of Multi-Target `.spec`:
  * Building both `RadioTVSegmenter.exe` (windowed GUI, `noconsole=True`) and `prs_worker.exe` (console worker, `console=True`) inside a single multi-target `.spec` file introduces severe Windows desktop risks:
    1. Subprocess Console Flashing: PyInstaller's C bootloader sets the PE subsystem flag at compile time. In multi-target specs sharing one bundle, child processes spawned by GUI apps frequently inherit or flash cmd.exe windows on Windows 11 unless compiled completely independently.
    2. Shared `_internal` and `sys.path` Polling Clashes: PyInstaller runtime hooks and import caches can cross-contaminate between the GUI app and the AI worker.
    3. High Implementation Complexity: Custom `.spec` files with shared `Analysis` objects are brittle across PyInstaller minor version upgrades.
- The Bulletproof Solution (Omit Redundant Wheel Collection in Stage 3):
  * Notice what `build_installer.py` Stage 3 already does: it runs PyInstaller to produce `prs_worker.exe` and then copies ONLY that single executable into `app_root`, completely discarding the newly generated `_internal` folder because `prs_worker.exe` runs adjacent to `app_root/_internal` (which Stage 1 already fully populated).
  * Why Stage 3 took 5m 45s: PyInstaller was passed `*torch_binary_flags` and `*collect_flags`, causing it to independently re-analyze and re-collect 1.2 GB of PyTorch, SciPy, and Torchaudio wheels via `pefile`.
  * The Fix: In Stage 3, invoke PyInstaller on `radio_tv_story_segmenter_worker.py` in `--console` mode without the redundant heavy wheel collection flags. PyInstaller produces the dedicated `prs_worker.exe` in ~15 seconds instead of 5m 45s.
  * Why this is superior to an external shim: It remains a real native Python console executable, guaranteeing that standard I/O pipes (`sys.stdout`/`sys.stderr`) work cleanly when spawned by `QProcess` in `processing.py`, and `multiprocessing.spawn` (`sys.executable -c ...`) works without crashing or flashing console windows.
  * Time Savings: Saves ~5m 30s with zero runtime or architectural risk.

[x] 2.2 Inno Setup Compression Optimization & Parallel Block Threads (`installer/Windows/RadioTVStorySegmenter.iss`)
--------------------------------------------------------------------------------
- The Problem: `RadioTVStorySegmenter.iss` specifies `Compression=lzma2/ultra64`, `SolidCompression=yes`, and `LZMAUseSeparateProcess=yes`, but omits `LZMANumBlockThreads`. By default, LZMA2 solid compression runs single-threaded, forcing a single core on the GitHub Actions runner to compress ~1.2 GB of uncompressed binaries with an intensive 64MB dictionary, resulting in the 10m 53s build time.
- The Solution:
  1. Multi-Core Consideration on GitHub Actions: Standard GitHub `windows-latest` runners provide only 2 vCPUs / 4 threads. While `LZMANumBlockThreads=2` utilizes all available virtual cores, threading alone only provides a ~1.4x–1.6x improvement.
  2. Algorithmic Optimization (The Primary Lever): Tune compression preset from `lzma2/ultra64` down to `lzma2/ultra` or `lzma2/max` with tuned block sizes. The `ultra64` 64MB match finder spends massive CPU cycles on diminishing returns for compiled binaries (<1MB difference on a ~180MB installer). Combining parallel block threads with `lzma2/max` or `lzma2/ultra` reduces Inno Setup compilation from 10m 53s to ~3–4 minutes (saving ~7 minutes).

[x] 2.3 PyInstaller Risk Pruning & Safe Exclusions (`build_installer.py`)
--------------------------------------------------------------------------------
- REJECTED as Too Risky: `--optimize 1` bytecode compilation.
  * Risk: Python `-O` strips docstrings (`__doc__`) and `assert` statements. Multiple scientific and AI libraries (PyTorch dynamo/JIT, HuggingFace transformers, tokenizers, ONNX Runtime, and docstring inspection helpers) have known runtime bugs or crashes when docstrings are stripped or assertions are disabled.
  * Benefit: PyInstaller bytecode compilation takes <3 seconds in total; `--optimize 1` provides negligible build speedup while introducing severe runtime risk.
- REJECTED as Too Risky: Pruning `torch.distributed` or `torch.testing`.
  * In v3.3.20, excluding `torch.distributed` caused a fatal `ModuleNotFoundError: No module named 'torch.distributed'` in speaker diarization and translation models on Windows. PyTorch internal imports depend on distributed stubs.
- Already Handled: Unused Qt modules (`PYSIDE6_EXCLUDES` covering `Qt3D`, `QtQuick`, `QtNetworkAuth`, `QtDesigner`, `QtSql`, etc.) and test suites (`TEST_AND_BENCHMARK_EXCLUDES` covering `scipy.*.tests`, `numpy.tests`, `sklearn.tests`) are already actively excluded in `build_installer.py`.
- Safe Scope: Keep PyInstaller analysis clean without aggressive, speculative module pruning.

[x] 2.4 CI Workflow Hygiene & Safe Caching (`.github/workflows/build.yml`)
--------------------------------------------------------------------------------
- Audited & Confirmed: `astral-sh/setup-uv@v5` already has `enable-cache: true` enabled in `build.yml`. Adding duplicate manual `actions/cache` steps would risk cache collisions and is redundant.
- REJECTED as Too Brittle: Caching Inno Setup compiler installation directory (`C:\Program Files (x86)\Inno Setup 6`). Chocolatey takes only 22 seconds; caching system program directories on Windows runners frequently causes missing registry keys, missing environment shims, or corrupt installations for an insignificant ~20-second gain.
- Safe Scope: Keep CI tool installation clean and rely on standard runner setup. Replace PowerShell `Invoke-WebRequest` with native `curl.exe -fSL --retry 3` for robust FFmpeg retrieval.

[ ] 4.1 Feature 1B — Persistent "Station Voicebook" (Cross-Show Speaker Library) (`speaker_identity.py`, `processing.py`)
--------------------------------------------------------------------------------
- The Problem: WeSpeaker diarization tags speakers as Speaker 1, Speaker 2. While the app has acoustic profile matching, users often have to re-identify their regular show hosts and anchors on every new recording.
- The Feature: A global Host & Anchor Voicebook. Save acoustic signatures for regular station hosts (e.g. "Jane Doe (Host)", "John Smith (News Anchor)"). Whenever a new recording is imported and diarized, the engine automatically matches and names known voices with a confidence percentage.
- Implementation: Extend `speaker_identity.py` to support persistent global acoustic voice profiles stored in user application data (`voicebook.json` / embeddings cache) and wire into `processing.py` diarization result parser.

[ ] 4.2 Feature 2A — Multi-Resolution Mipmapped Waveform Peak Cache (LOD Rendering) (`processing.py`, `background_workers.py`, `timeline_widgets.py`)
--------------------------------------------------------------------------------
- The Problem: When loading 2-to-4-hour broadcast files (e.g. morning radio blocks or city council meetings), zooming and rapid timeline scrubbing can stutter because the painter traverses millions of raw peak samples.
- The Feature: Implement Level-of-Detail (LOD) downsampled peak tiers (1x, 4x, 16x, 64x zoom levels) in `background_workers.py` and `processing.py`. When zoomed out, the timeline paints from the highest-downsampled tier; as you zoom in, it dynamically switches to the high-resolution tier.
- Status & Architecture: The in-memory pyramid generator (`build_waveform_pyramid`) currently exists in `timeline_widgets.py`, but peaks are not persisted with multi-resolution tiers to the `.peaks` binary cache on disk. Persisting precomputed mipmapped tiers directly into `.peaks` files will deliver instantaneous file loading and locked 60fps scrubbing on hours-long recordings.

[ ] 4.3 Feature 3A — Speed-Listening "Type-to-Correct" Proofreading Workflow (`transcript_editor.py`, `RadioTVSegmenter.py`)
--------------------------------------------------------------------------------
- The Problem: Proofreading transcripts at 1.0x speed is slow.
- The Feature: A dedicated proofreading mode: audio plays back at 1.25x or 1.5x speed with pitch preservation (time-stretching via WSOLA/QMediaPlayer playback rate, preventing "chipmunk" distortion) while highlighting each word in real-time. Hitting `Tab` pauses audio and places the cursor on the current word for instant editing; pressing `Tab` again auto-resumes playback.
