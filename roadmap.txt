--------------------------------------------------------------------------------
ROADMAP MAINTENANCE POLICY: N-1 SLIDING-WINDOW & STATUS TRACKING
--------------------------------------------------------------------------------
- The roadmap maintains a rolling window: it displays the current/immediate past
  release ($N-1$) for baseline context, followed by active upcoming development
  milestones ($N$, $N+1$).
- Status Notation Policy (Modeled after Social Digest):
  * All milestones and feature items are annotated with explicit progress indicators:
    - [x] Completed item / feature
    - [-] In-progress item / active development
    - [ ] Planned / not started item
  * When work commences on an item, mark it immediately as [-] [IN-PROGRESS].
  * Mark an item as [x] [COMPLETED] when implementation is finalized, upon user
    confirmation, or inferred when development transitions to another part of the roadmap.
- ARCHITECTURAL DETAILS & CROSS-REFERENCE DIRECTORY:
  * To maintain strict file-budget hygiene and avoid token bloat, comprehensive code-level
    audits, call stacks, repro evidence, and diffs are preserved in dedicated technical documents:
    - Code Audit Findings & Bug Fixes: `docs/audit/audit_phase1_findings.md` through `audit_phase7_findings.md`
    - Master Audit Plan & Prioritization: `docs/audit/audit_roadmap.md`
    - Subsystem Architecture & IPC Specifications: `ARCHITECTURE.md`
    - Release Logs & Historical Commits: `CHANGELOG.md`
- "WHAT'S NEXT" PROTOCOL FOR AI STUDIO:
  * Whenever the user asks "what's next" (or asks for an update on the roadmap), DO NOT immediately modify code or take action.
  * State what is next on the roadmap, outline the issue or feature, and suggest possible next steps.
  * STOP and wait for the user to confirm whether they would like to proceed before making any changes.
  * When implementing confirmed tasks:
    - NEVER combine multiple sub-items in a single response unless requested.
    - NEVER truncate any file with placeholders (`# ... existing code ...`).
    - ALWAYS preserve 100% backward compatibility by re-exporting all extracted classes,
      functions, and constants in the original facade module and `prs_shared.py`.
    - ALWAYS keep every new or modified `.py` file under the 1,000-line ceiling (~800 lines target).
