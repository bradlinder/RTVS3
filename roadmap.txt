RADIO & TV STORY SEGMENTER - DEVELOPMENT ROADMAP & TECHNICAL SPECIFICATION

This document outlines the architectural roadmap and implementation specifications
for future versions of the Radio & TV Story Segmenter. Adapted from best-in-class
heuristics, modular runtime architectures, and timeline serialization algorithms.

--------------------------------------------------------------------------------
ROADMAP MAINTENANCE POLICY: N-1 SLIDING-WINDOW & STATUS TRACKING
--------------------------------------------------------------------------------
- The roadmap maintains a rolling window: it displays the current/immediate past
  release ($N-1$) for baseline context, followed by active upcoming development
  milestones ($N$, $N+1$).
- Status Notation Policy (Modeled after Social Digest):
  * All milestones and feature items are annotated with explicit progress indicators:
    - [x] Completed item / feature
    - [-] In-progress item / active development
    - [ ] Planned / not started item
  * When work commences on an item, mark it immediately as [-] [IN-PROGRESS].
  * Mark an item as [x] [COMPLETED] when implementation is finalized, upon user
    confirmation, or inferred when development transitions to another part of the roadmap.
- When a new version is built, its completed specifications are recorded, and any
  versions older than $N-1$ are pruned to keep the document focused and actionable.
- Whenever any code change, bug fix, packaging adjustment, or feature refinement is
  made during a release cycle, it MUST be recorded immediately in the current release
  section of roadmap.txt and CHANGELOG.md (even if it occurs after the initial version
  number bump).

CORE ARCHITECTURAL INVARIANTS
================================================================================
- Core modules must NEVER import from plugins/.
- Heavy translation runtimes must remain isolated inside plugins/translation/.
- Speaker diarization uses wespeakerruntime as the primary ONNX embedding engine.
- Real-time progress updates with percentage, status messages, and estimated time.
- Diagnostic logs written to OS standard logging locations.
- Offline-first architecture: core processing functions locally without internet.
- 0 MB Default GPU Footprint: Base installer contains 0 MB of CUDA bloat; GPU features are purely optional and provisioned on demand.

3. UPCOMING MILESTONE: PHASE 2 MODULARIZATION OF PRS_SHARED.PY (UI & Qt Components) [PLANNED]
================================================================================

Proceed with extreme caution: unlike Phase 1's pure-Python modules, Phase 2 components are tightly coupled to PySide6/Qt signals, slots, widget parenting hierarchies, and paint events.

[ ] 4.1 CAUTIOUS TESTING & VERIFICATION METHODOLOGY (Protocol for Every Single Extraction)
------------------------------------------------------------------------------------------
To avoid cascading regressions or subtle Qt widget crashes, execute the following 5-step cycle for EACH extracted component module:
1. **Isolated Module Extraction**:
   - Extract only ONE logical domain at a time (e.g. `cache_manager` first, which has minimal Qt widget hierarchy).
   - Identify all internal dependencies and verify whether they need to import from `prs_shared.py` or base Qt modules.
2. **Re-Export Shim Installation**:
   - Add explicit re-export shims in `prs_shared.py` (`from <new_module> import *`) immediately so external callers remain 100% intact.
3. **Multi-Tier Syntax & Compilation Verification**:
   - Run `python -m py_compile <new_module>.py prs_shared.py RadioTVSegmenter.py ui_layout.py transcript_story.py processing.py`.
4. **Headless Import & Symbol Verification**:
   - Run automated headless script checking:
     * Module importability without cyclical import errors.
     * All expected classes, signals, and functions are present and callable.
     * Instantiation of non-widget classes and default dataclasses/namedtuples.
5. **Interactive UI Smoke Check & Snapshot**:
   - Verify widget instantiation in offscreen/test mode.
   - Run web preview linter & compiler (`lint_applet` & `compile_applet`).
   - Create a rollback checkpoint or snapshot before moving to the next module.

[ ] 4.2 TARGET MODULE EXTRACTION SEQUENCE
-----------------------------------------
- **Step 1: `cache_manager.py` (Low-to-Medium Risk)**:
  * Targets: `format_byte_size`, `get_cache_disk_usage`, `cleanup_old_thumbnail_cache`, `ClearCacheDialog`, `VideoThumbnailCache`.
  * Dependencies: PySide6 QDialog/QThread, `core_utils`.
- **Step 2: `story_widgets.py` (Medium Risk)**:
  * Targets: `StoryListWidget`, `StoryItemWidget`, `StoryCardWidget`, `StoryMetadataDialog`, drag-and-drop file queues.
  * Dependencies: PySide6 QListWidget, custom signals (`filesDropped`), styling sheets.
- **Step 3: `timeline_widgets.py` (Medium-to-High Risk)**:
  * Targets: `TimelineRulerWidget`, `TimelineTrackWidget`, `PlayheadOverlay`, waveform peak painting, coordinate-to-time mapping.
  * Dependencies: QPainter, custom paint events, audio time conversion.
- **Step 4: `transcript_editor.py` (High Risk)**:
  * Targets: `TranscriptTextViewer`, `TranscriptSegmentWidget`, word-level span highlighting, search-and-replace dialog.
  * Dependencies: QTextEdit/QPlainTextEdit, cursor manipulation, speaker coloring, audio synchronization slots.

5. FUTURE MILESTONE: GOOGLE DOCS & DRIVE EXPORT PLUGIN (Planned for v3.5) [NOT STARTED]
================================================================================

Architectural Objective:
Implement Google Docs & Drive export as a dedicated, self-contained export plugin (`plugins/gdocs/`) rather than integrating directly into the core desktop binary.

Key Architectural & Packaging Benefits:
- Core Binary Savings: Avoids bundling official Google client libraries (`google-api-python-client`, `google-auth`, etc.) or cloud SDK stubs in the core PyInstaller distribution, saving 20-45 MB uncompressed disk footprint and 10-18 MB in the installer executable.
- Zero Memory / Startup Impact: Utilizes RTVS lazy plugin registration so offline-first users incur zero overhead or dependency initialization at launch.
- Security & Credential Isolation: Encapsulates OAuth 2.0 client credentials, user authorization scopes (`drive.file`, `documents`), and refresh tokens strictly within plugin-scoped secure OS keyring storage.
- Independent Release Cadence: Allows updating OAuth flows or Google Docs API formatting logic via standalone `.rtvs-addon` packages without requiring a rebuild of the full native desktop app.

[ ] 5.1 Plugin Scaffolding & OAuth 2.0 Auth Engine (`plugins/gdocs/auth.py`)
-------------------------------------------------------------------------
- Create `plugins/gdocs/manifest.json` (category: "export", lazy-enabled) and plugin base class implementation in `plugins/gdocs/plugin.py`.
- Build an isolated OAuth 2.0 authorization module supporting loopback redirect on localhost (`127.0.0.1:port`) for seamless browser-based user sign-in.
- Securely persist refresh tokens using the OS keyring (`keyring` module already present in core requirements) with manual disconnect/revoke capability in plugin preferences.

[ ] 5.2 Google Docs Document Serializer & REST Exporter (`plugins/gdocs/formatter.py`, `client.py`)
-------------------------------------------------------------------------------------------------
- Implement lightweight Google Docs REST client using Python's standard `requests` library (avoiding heavy external Google SDK dependencies).
- Serialize segmented transcript data into structured Google Docs `batchUpdate` requests:
  * Document header: Broadcast title, date, total duration, detected speakers, and story summary table.
  * Story headings & cards: Heading styles, story metadata tables (word count, duration, in/out points).
  * Styled transcript body: Speaker name badges with distinct colors, italicized timecode markers, and preserved word-level text highlights (`backgroundColor` style updates matching Word/DOCX styles).

[ ] 5.3 Native Margin Comments & Annotation Anchoring (`plugins/gdocs/comments.py`)
---------------------------------------------------------------------------------
- Map RTVS story notes and transcript inline comments directly to native Google Drive margin comments via `drive.comments.create`.
- Anchor comments to corresponding text ranges or paragraph spans in the generated document using Google Docs document range offsets.

[ ] 5.4 Unified Export Center & Menu Integration
----------------------------------------------
- Register the Google Docs export destination in the Unified Export Center and the main window Transcript menu ("Export" -> "Export to Google Docs...").
- Provide a non-blocking asynchronous export worker with progress bar updates, rate-limiting retry handling, and direct "Open in Google Docs" link generation upon completion.

[ ] 5.5 (Optional) One-Time Review & Comment Pull ("Import Reviews from Google Doc")
-----------------------------------------------------------------------------------
- Add an optional menu action to fetch updated margin comments or suggested edits from a linked Google Doc.
- Present changes in a non-destructive review diff dialog, allowing the editor to selectively accept or dismiss comments without breaking word-level audio alignment.
