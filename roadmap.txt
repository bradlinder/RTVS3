This document outlines the architectural roadmap and implementation specifications
for future versions of the Radio & TV Story Segmenter. Adapted from best-in-class
heuristics, modular runtime architectures, and timeline serialization algorithms.

--------------------------------------------------------------------------------
ROADMAP MAINTENANCE POLICY: N-1 SLIDING-WINDOW & STATUS TRACKING
--------------------------------------------------------------------------------
- The roadmap maintains a rolling window: it displays the current/immediate past
  release ($N-1$) for baseline context, followed by active upcoming development
  milestones ($N$, $N+1$).
- Status Notation Policy (Modeled after Social Digest):
  * All milestones and feature items are annotated with explicit progress indicators:
    - [x] Completed item / feature
    - [-] In-progress item / active development
    - [ ] Planned / not started item
  * When work commences on an item, mark it immediately as [-] [IN-PROGRESS].
  * Mark an item as [x] [COMPLETED] when implementation is finalized, upon user
    confirmation, or inferred when development transitions to another part of the roadmap.
- When a new version is built, its completed specifications are recorded, and any
  versions older than $N-1$ are pruned to keep the document focused and actionable.
- Whenever any code change, bug fix, packaging adjustment, or feature refinement is
  made during a release cycle, it MUST be recorded immediately in the current release
  section of roadmap.txt and CHANGELOG.md (even if it occurs after the initial version
  number bump).

3. UPCOMING MILESTONE: WINDOWS CI BUILD SPEED & PACKAGING OPTIMIZATION [PLANNED for v3.8.9] [CI/BUILD] [NOT STARTED]
================================================================================

[ ] 3.1 Unified Single-Pass Multi-Target PyInstaller Spec Build (`build_installer.py`)
--------------------------------------------------------------------------------
- The Problem: Currently, PyInstaller runs twice in sequence — once for `RadioTVSegmenter.exe` and once for `prs_worker.exe`. Both runs perform heavy module dependency analysis and package collection for shared libraries (`PySide6`, `onnxruntime`, `torch`, `whisper`, etc.), taking ~8 to 10 minutes total.
- The Solution: Generate a unified multi-target `.spec` file that performs single-pass analysis on shared dependencies and emits both `RadioTVSegmenter.exe` and `prs_worker.exe` in one compilation run, cutting ~4 to 5 minutes off build times.

[ ] 3.2 Inno Setup Multithreaded LZMA2 Compression & Parallel Worker Mode (`installer/Windows/RadioTVStorySegmenter.iss`)
--------------------------------------------------------------------------------
- The Problem: `Compression=lzma2/ultra64` with `SolidCompression=yes` achieves maximum installer compression, but runs single-threaded by default, spending 3 to 5 minutes compressing the staged distribution on 4-core GitHub Actions runners.
- The Solution: Configure `LZMANumBlockThreads=max` (or `4`) and `LZMAUseSeparateProcess=yes` in the Inno Setup script to parallelize LZMA2 block compression across all available vCPUs, reducing Inno Setup build time from ~5 minutes to ~1.5 minutes with identical output file size.

[ ] 3.3 Bytecode Optimization & Pruned AST Collection (`build_installer.py`)
--------------------------------------------------------------------------------
- Pass `--optimize 1` to PyInstaller to strip docstrings and accelerate Python bytecode compilation.
- Exclude unnecessary test packages, documentation trees, and typing stubs from PyInstaller analysis graphs.

[ ] 3.4 GitHub Actions Workflow Download & Tool Caching Acceleration (`.github/workflows/build.yml`)
--------------------------------------------------------------------------------
- Replace PowerShell `Invoke-WebRequest` with native `curl.exe -fSL --retry 3` for robust, parallel downloads of external tools (FFmpeg, etc.).
- Add GitHub Actions caching (`actions/cache`) for Inno Setup compiler installations to bypass Chocolatey install overhead on warm CI runs.

5. FUTURE MILESTONE: CORE BROADCAST VOICEBOOK, PEAK LOD CACHE & SPEED-LISTENING ENGINE [PLANNED for v3.9.0] [CORE] [NOT STARTED]
================================================================================

[ ] 5.1 Feature 1B — Persistent "Station Voicebook" (Cross-Show Speaker Library) (`speaker_identity.py`, `processing.py`)
--------------------------------------------------------------------------------
- The Problem: WeSpeaker diarization tags speakers as Speaker 1, Speaker 2. While the app has acoustic profile matching, users often have to re-identify their regular show hosts and anchors on every new recording.
- The Feature: A global Host & Anchor Voicebook. Save acoustic signatures for regular station hosts (e.g. "Jane Doe (Host)", "John Smith (News Anchor)"). Whenever a new recording is imported and diarized, the engine automatically matches and names known voices with a confidence percentage.
- Implementation: Extend `speaker_identity.py` to support persistent global acoustic voice profiles stored in user application data (`voicebook.json` / embeddings cache) and wire into `processing.py` diarization result parser.

[ ] 5.2 Feature 2A — Multi-Resolution Mipmapped Waveform Peak Cache (LOD Rendering) (`processing.py`, `background_workers.py`, `timeline_widgets.py`)
--------------------------------------------------------------------------------
- The Problem: When loading 2-to-4-hour broadcast files (e.g. morning radio blocks or city council meetings), zooming and rapid timeline scrubbing can stutter because the painter traverses millions of raw peak samples.
- The Feature: Implement Level-of-Detail (LOD) downsampled peak tiers (1x, 4x, 16x, 64x zoom levels) in `background_workers.py` and `processing.py`. When zoomed out, the timeline paints from the highest-downsampled tier; as you zoom in, it dynamically switches to the high-resolution tier.
- Status & Architecture: The in-memory pyramid generator (`build_waveform_pyramid`) currently exists in `timeline_widgets.py`, but peaks are not persisted with multi-resolution tiers to the `.peaks` binary cache on disk. Persisting precomputed mipmapped tiers directly into `.peaks` files will deliver instantaneous file loading and locked 60fps scrubbing on hours-long recordings.

[ ] 5.3 Feature 3A — Speed-Listening "Type-to-Correct" Proofreading Workflow (`transcript_editor.py`, `RadioTVSegmenter.py`)
--------------------------------------------------------------------------------
- The Problem: Proofreading transcripts at 1.0x speed is slow.
- The Feature: A dedicated proofreading mode: audio plays back at 1.25x or 1.5x speed with pitch preservation (time-stretching via WSOLA/QMediaPlayer playback rate, preventing "chipmunk" distortion) while highlighting each word in real-time. Hitting `Tab` pauses audio and places the cursor on the current word for instant editing; pressing `Tab` again auto-resumes playback.
